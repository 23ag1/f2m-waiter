# Статусы столов — контракт фронт ↔ бэкенд

## Цвета статусов (официальная схема iikoWaiter)

Взято из документации/справки iikoWaiter (см. «Источники» внизу). Так iiko
раскрашивает заказ по стадии жизненного цикла:

| Стадия | `status` (ключ фронта) | Ярлык на карточке | Цвет |
|---|---|---|---|
| Новый заказ, блюда **не отпечатаны** | `new` | Новый заказ | 🔵 синий |
| Блюда **отпечатаны** (отправлены на кухню) | `printed` | Блюда отпечатаны | ⚫ чёрный |
| Блюда **готовы** | `ready` | Блюда готовы | 🟢 зелёный |
| Блюда **поданы** | `served` | Блюда поданы | ⚪ серый |
| Напечатан **пречек** (редактировать нельзя) | `precheck` | Пречек напечатан | 🔴 красный |

Фронт уже реализует ровно эту схему (цвет заголовка + цветной кружок-индикатор +
цвет подписи). Логика — в `src/entities/table/model/status.ts` (`STATUS_STYLES`).

## Что нужно от бэкенда

`GET /api/v1/waiter/active-tables` сейчас возвращает по столу:
`id, table_number, total_price, dish_count, dish_names, guests, created_at`.
**Поля `status` НЕТ** — поэтому фронт временно рисует статус по возрасту заказа
(`created_at`), это заглушка и НЕ отражает кухню.

Нужно добавить в каждый объект стола строковое поле **`status`**:

```jsonc
{
  "tables": [
    {
      "id": 123,
      "table_number": "12",
      "status": "ready",          // <-- ДОБАВИТЬ (одно из значений ниже)
      "created_at": "2026-06-28 17:40:00",
      "total_price": 1240,
      "dish_count": 3,
      "dish_names": ["..."],
      "guests": [ ... ]
    }
  ]
}
```

Как только поле придёт — фронт сам начнёт использовать реальный статус
(`getStatus()` предпочитает `status`, а на временную логику откатывается только
когда поля нет). Менять на фронте больше ничего не надо.

## Допустимые значения `status` (уже маппятся на фронте)

Маппинг регистронезависимый, живёт в `BACKEND_STATUS_MAP`. Принимаются синонимы:

| Реальный `status` от бэка | → ключ | Цвет |
|---|---|---|
| `new`, `created`, `open`, `sent`, `cooking`, `not_printed` | `new` | 🔵 синий |
| `printed`, `fired`, `sent_to_kitchen`, `kitchen` | `printed` | ⚫ чёрный |
| `ready`, `done`, `cooked`, `prepared` | `ready` | 🟢 зелёный |
| `served`, `delivered` | `served` | ⚪ серый |
| `precheck`, `bill`, `bill_printed`, `check`, `closing`, `closed` | `precheck` | 🔴 красный |

Неизвестная строка → фронт молча откатится на временную логику. Если бэк шлёт
другие строки — допишите их в `BACKEND_STATUS_MAP` (одно место).

## Статус отдельного блюда (per-dish)

Та же история на уровне позиции корзины. iiko красит каждое блюдо по его
кухонному статусу и меняет поведение:

| Статус блюда | Цвет | Поведение |
|---|---|---|
| не отправлено (в корзине) | 🔵 синий | курс **можно** менять |
| отправлено на кухню | ⚫ чёрный | курс **заблокирован**, показывается «готовится» |
| готово | 🟢 зелёный | показывается «готово»; тап → «подано» |
| подано | ⚪ серый | показывается «подано» |

Фронт это уже реализует (`src/entities/dish/model/dish-status.ts`), читая
необязательное поле **`status`** у каждого элемента `basket[]` в ответах
`GET /waiter/basket/{clientId}` и `active-tables.guests[].basket`. Пока бэк это
поле не шлёт → все блюда считаются «не отправлено» (синий, курс выбирается).

Нужно от бэка: добавить `status` в каждый объект блюда корзины. Значения — те же
строки, что в таблице выше (маппинг в `DISH_STATUS_MAP`). Тап «готово → подано»
заработает, когда блюдо реально будет приходить со статусом `ready`.
